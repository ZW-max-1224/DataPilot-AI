**第 1 步：打开页面，先讲定位（20 秒）**

**第 2 步：左侧选"使用 Demo 数据"，展示数据画像（40 秒）**

> "上传后系统自动做数据画像：行列数、缺失值、重复值、字段语义类型、质量评分。质量分是**透明的规则估算**，不是黑盒——每个扣分项都写明了依据。"

**第 3 步：问"为什么 8 月销售额下降？"（90 秒，核心）**

在 Agent 区域提问，等它跑完。指着"分析步骤"说：

> "注意它调了两次工具：先 `calculate_time_series` 看月度趋势，再 `calculate_correlation` 找相关因素。这是 Agent 而不是聊天机器人的关键——**Reason → Tool → Observation → Reason → Tool → Answer**。"

**第 4 步：指着结构化结论（60 秒，这是最亮的点）**

> "最终回答不是一段自由文本，而是结构化的：总体结论、关键发现、建议。**最关键的是每条结论都有标签**：✅ 事实、🔎 解释、⚠️ 假设。
>
> 标为"事实"的结论必须有一个**真实运行过的工具**作为证据——这是**代码强制的**，不是靠 Prompt 请求。如果模型标了 fact 但拿不出对应的工具调用，系统会自动把它降级为"假设"。这样模型永远没法把猜测说成事实。"

**第 5 步：展示图表和双语（30 秒）**

问"画一张各月销售额的折线图"，然后切换左上角语言到 English：

> "模型只负责选择图表参数（类型、X、Y、分组），真正画图是服务端的 Matplotlib。界面完整支持中英文。"

**第 6 步：收尾（20 秒）**

> "整个项目 244 个离线测试、GitHub Actions CI 全绿、ruff 无告警。Agent 链路、LLM 调用、Embedding→RAG 检索都是用真实服务端到端验证过的；MySQL 和 LangSmith 目前还没验证，我在 README 里如实标注了。"

## 二、六个必答问题

### Q1：为什么需要 Agent？直接调一次 API 让人家自己分析不行吗？

> "因为数据分析任务不是固定流程。'为什么 8 月下降'需要先看趋势、再定位到区域或品类；'找出 Top 10 产品'只需要一次聚合。不同问题需要不同的工具组合，而**这个组合要由模型根据数据反馈动态决定**。固定 pipeline 要么写死一堆 if-else，要么每次都调全部工具浪费成本。Agent 的价值就是'根据观察决定下一步'。"

### Q2：为什么不让 LLM 直接执行 Python？

> "安全和可控。让模型生成代码再 `exec` 有两个问题：一是模型可能生成删除文件、访问网络、读取项目外文件的代码；二是生成错了很难定位。所以我用**白名单工具**：`app/tools/registry.py` 里显式注册了 10 个工具，模型只能填参数，参数还要过 Pydantic 校验。分发是 `MappingProxyType` 上的精确字典查找，**没有动态导入、没有 exec/eval、没有任意 SQL 或 Shell**。项目里搜不到这些关键字。"

### Q3：为什么结论不让 LLM 直接生成，还要用 Pandas 算？

> "LLM 擅长理解问题和规划步骤，但不擅长准确计算。'12 个月销售额'这种数字如果让模型自己说，很容易编。所以**真实计算全部交给 Pandas，模型只负责解释**。这样既降低幻觉，也让结果可复现——同一个问题跑两次数值完全一致。"

### Q4：你的项目 244 个测试全绿，那它一定可靠吗？

> "**恰恰相反，我踩过这个坑，这是我项目里最有价值的一段经历。**
>
> 我前 6 个阶段都是 Mock 测试，149 个测试全绿。等我把真实的 LLM Key 配好做端到端验收时，成功率只有 **1/10**。原因是 Mock 覆盖不到真实故障：模型会偶发把 JSON 包进 Markdown 代码块、网络会瞬时中断、模型会猜错列名。
>
> 我做了故障归因，定位到四类根因并逐一修复，最后真实成功率从 1/10 提到 **6/6**。这件事让我明白：**Mock 全绿不等于系统可用**，端到端验收不能省。"

### Q5：为什么没用 LangChain / LangGraph？你的项目不是要学这些吗？

> "我一开始评估了 LangChain，最后决定不用，理由是：**这个项目的核心是 Agent 的可控性和可观测性，而不是编排框架的便利性。**
>
> 具体来说我需要控制几件框架默认不让我控制的事：一是工具白名单必须是我自己的静态注册表（精确字典查找，不给动态导入留口子）；二是模型输出的 JSON 契约要能被 Pydantic 严格校验并且失败后能修复重试；三是**每次决策的 prompt 必须在硬预算内，超了要有明确的分级降级顺序**。这些用普通 Python 写反而更短更透明。
>
> 我读懂了 Agent 循环的本质是自己实现了一遍：`LLM 返回决策 → 校验 → 执行工具 → 结果回灌 → 再决策`，加上最大 8 轮、结果 3000 字符上限、prompt 16000 字符硬上限。**我能解释每一行，而不是调一个 `AgentExecutor` 就交差。** LangGraph 我留给下一阶段——当流程真的需要持久化状态和分支图的时候再引入。"

### Q6：这个项目最难的部分是什么？

> "**让 Agent 在出错时还能继续，并且不丢证据。**
>
> 我第一版的循环是'一次不对就终止'——工具报错就失败、JSON 解析失败就失败、模型调用失败就失败。结果是用户问一个问题，模型猜错一个列名，前面 4 次工具调用算出来的数据全丢了，只返回一句'工具参数不匹配'。
>
> 我改成：可恢复的工具错误作为**观察值回灌**给模型（'没有 revenue 这一列，可用列是……'），让模型自己改成正确的列名重试，同一工具连续错 2 次才熔断；JSON 解析失败把校验错误回灌重试 2 次；模型调用失败保留已算出的证据，在最终回答里标注'本次分析未完整结束'而不是只说一句错误。
>
> 另外还有一类很隐蔽的失败：**模型偶尔会把工具参数里的键名取成 `name`，而 Python 在参数绑定阶段就会抛 `TypeError`——那时候我的校验代码还没执行**，异常直接逃出整个 Agent。我改成把模型参数作为**一个数据对象**传入，而不是 `**` 展开，这样可信参数（比如知识库 ID）和数据参数在命名空间上就是隔离的。"

## 三、五个可以讲的技术故事（STAR）

| # | 故事 | 面试价值 |
|---|---|---|
| **1** | **Mock 全绿但真实只有 1/10**：端到端验收发现模型会把 JSON 包进 ```` ```json ```` 围栏、网络会瞬时中断、工具错误无法自我纠正、模型参数与函数参数命名冲突导致崩溃。四类根因逐一修复，成功率 1/10 → 6/6。 | 展示"不满足于测试通过"、故障归因能力和系统思维 |
| **2** | **严格性用错了地方**：我给 Agent 加结构化输出后，成功率从 10/10 **掉回 4/6**。原因是把 `claim_type` 写成严格枚举，模型返回的等价变体（`"conclusion"`、字段名叫 `claim`）让整个决策校验失败。我把严格性重新分配：安全关键字段（action/tool_name/tool_input）保持严格，展示字段做归一化解析。 | 展示工程判断力，以及"能发现自己引入的回归" |
| **3** | **宽容解析造成了静默数据丢失**：上一条的宽容解析第一版用了 `extra="ignore"` + 默认空字符串，结果模型的结论放在 `claim` 键、建议放在 `{"text": ...}` 里，**全部被静默丢掉**（`findings=0`）。我没有猜，而是写探针抓到了模型原始输出里的真实键名，据此加别名表，并加了"非空输入却解析出 0 条就告警"的日志。 | 展示"用证据而不是猜测定位问题"，以及可观测性意识 |
| **4** | **检索不可用时，模型的通用知识被伪装成知识库证据**：RAG 验证时发现，知识库不可用时模型仍用自己的知识回答"什么是毛利率"，但运行标记成功、工具记为已调用、步骤说"获取结构化分析结果"——用户会以为那是知识库给的。我加了 `retrieval_status`（ok/no_results/unavailable）、状态感知的步骤摘要、Prompt 强制声明和 UI 警告条。 | 直接对应项目的"不要伪造 AI"原则，展示数据诚信意识 |
| **5** | **测试不隔离：本地红、CI 绿**：UI 测试读取开发者真实的 `.env`。我一配置 Embedding，知识库区才开始渲染上传框，`file_uploader[0]` 就从数据集上传框变成了知识库上传框。CI 没有 `.env` 所以永远发现不了。修复：autouse fixture 隔离环境 + 按 key 定位组件 + 一条**显式证明隔离成立**的测试。 | 展示对"测试可靠性"的理解，这是很多应届生答不出来的 |

**故事 4 的补充说法（最能打动面试官）：**"我的原则是：**没有来源的内容必须明确标注没有来源**。宁可告诉用户'这次没检索到，以下是通用知识'，也不能让回答看起来像有依据。产品上这叫可信度，技术上这是把'诚实'写进代码而不是写进 Prompt。"

> "下一步我优先做的是：把 mypy 清零并启用 ruff 的 E501/I001 让 CI 门禁完整；然后把 RAG 评估数据集扩充成带干扰项和改写问题的版本；再往后是引入 LangGraph 做有状态的长流程。FastAPI 和 Docker 我放在最后——现在 Streamlit 已经能完整演示，提前上服务化只会增加简历上不痛不痒的复杂度。"

## 六、演示时的禁忌（会当场露馅）

1. **别说"用了 LangChain / LangGraph / MySQL / RAG 框架"**——项目用的是原生 SDK 和自研 Agent 循环；MySQL 代码写了但未真实验证。
2. **别说"RAG 效果很好"**——RAG 检索链路已验证（会命中对的文档），但**效果基准没做过**，要说"检索链路可用，效果评估是下一阶段"。
3. **别把 Demo Mode 说成 AI 在运行**——没有 Key 时它会明确显示 Demo Mode，这正是设计的一部分。
4. **别说"测试覆盖率 100%"**——项目没有覆盖率目标，也还没测覆盖率。
5. **别背 README**——文件里写的是给读者看的，你要讲的是**为什么这么做**和**踩了什么坑**。
